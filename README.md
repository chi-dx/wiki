# wiki

当前已试接真实的`llm-wiki-compiler@1.3.0`与DeepSeek Flash，调用上游`wiki.query()`。本机已完成8篇虚构资料的真实模型编译及两条问答链路验证；新环境仍需自行配置`DEEPSEEK_API_KEY`。配置、启动和验证边界见 [Compiler试接说明](docs/compiler-trial.md)。

初版的模块职责、问答流程和部署架构图见 [技术架构文档](docs/architecture.md)。

可运行初版已提供：8篇虚构Wiki、3篇模拟外部资料、知识编译、本地检索、原文引用和反馈。启动与真实接口接入方式见 [运行说明](docs/running.md)。llm-wiki明确指[Karpathy的设计思路](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)，不是第三方解析库；本项目据此实现持久化知识层，详见[实现说明](docs/llm-wiki.md)。未配置模型时生成摘录和目录，不声称已完成LLM综合。

团队目前约200人，文档散落在各自的WIKI，大概有如下内容，我们希望建立一个知识库
## 知识库说明
知识库是一个团队内公开、跨团队共享的承载现有业务知识、经验沉淀的地方，包含范畴（暂定）：
1、团队沉淀的工具武器库、分析方法知识库——遇到问题求人不如求图书馆
基础分析工具：nmon、火焰图、perf、ftrace、...（参考brendangregg体系）
高阶分析工具：HPM、advisor、...
智能调优工具：DSE、CMF、※KPBot
2、团队沉淀的穿刺/优化经验案例、客户POC案例——了解其他人是怎么从0到1做成和我类似的事情
客户案例：A+K算子下发、spark velox优化、沙箱拉起耗时、...
穿刺案例：simdjson、folly、...
3、业务全景图，真图，可点的——大数据入手
4、团队看护的核心应用、加速库的性能数据看板、火焰图等指标归档(链接)——性能现状和优化穿刺带来的效果
5、团队持续挖掘的芯片需求看板——做深芯片能力
6、团队持续提交的社区pr看板——做大鲲鹏生态
7、业界技术峰会日程
例如，flink参会总结、lance多模态数据结构，来自周二技术评审、周五SEG
8、团队high level的技术洞察，鲲看、SEG等材料——了解前瞻动向，看到趋势
p.s. 要有哪些region：
鲲鹏ARM新指令、鲲鹏硬件特性如DPA （想了解芯片能力，软硬结合，不知道如何下手）
NEON/SVE/SVE2向量化专区（想搞向量化优化，但没弄过，不知道如何下手）
迭代管理专区（带一个商用迭代，流程不会，只能，出包、安全编译疏忽导致被提单，踩坑踩不完；缺少专业checklist）
性能优化方法专区（一个问题POC、一个新场景定义，没有标准化runbook，导致出现诸如没绑核就测数据、没评审规格和数据集就测数据，导致数据波动、不可靠，一周甚至一个月白干）
Profiling专区（基础如火焰图、perf；高阶如SPE、HPM等）
Topdown经验专区
芯片属性专区（例如l1 l2 l3大小等基本信息，来自芯片出口、芯片竞分）
## 技术思路
1. 将目前的文档迁移到一个固定的知识库，分好区后号召各团队做迁移
2. 迁移后做一个门户页面，分板块快速跳转到对应的wiki等，主要都是超链接
3. 门户提供搜索框，后端检索资料并生成带原文引用的回答，同时返回相关文档链接
4. 回答后提示用户反馈是否解决问题，用于后续改进内容和检索效果

### 第一版范围

- 仅团队内使用，暂不考虑权限设计
- 仅提供单次问答，不提供多轮对话，不保存用于后续问答的会话上下文
- 后端采用固定流程调用模型API，不使用Claude Code或自主Agent作为搜索入口
- 知识编译层参考Karpathy的llm-wiki思路，将原始资料整理为持久化知识页；后端负责同步调度、检索调用、资料融合、回答生成和反馈记录
- 初版覆盖门户导航、文档同步与索引、单次检索问答和用户反馈
- 文档维护不在初版范围内：不做负责人管理、AI质量巡检、Wiki评论提醒或维护处理流程；源文档变化后的同步与索引更新仍属于初版
- 暂不建设正式验收题集和量化验收标准，先通过用户反馈收集改进线索

### 文档同步与索引

1. 通过Wiki接口获取文档及同步所需元数据，初版不依赖评论接口
2. 文档规模预计不超过1,000份，每篇平均两三页，首次全量同步到服务器
3. 后续定期检查文档版本；没有可用版本字段时，对内容计算哈希，仅对变化文档重新解析和更新索引
4. 保存源文档ID、标题、原文链接、源更新时间、版本或内容哈希，以及同步状态
5. 知识编译层生成资料页、主题页、目录和关联链接，保存原文映射；模型编译需显式启用，无模型时仅生成摘录与目录
6. 确认源文档删除后移除对应索引；拉取失败不视为删除，记录失败并重试

### 单次问答流程

1. 用户在门户提交问题，后端先检索编译知识页，再根据来源映射获取原文证据
2. 按需调用hisi第三方API，获取公共资料作为外部参考
3. 后端将问题与检索证据交给模型生成回答：关键结论引用原文，明确区分“内部实践”和“外部参考”
4. 找不到相关资料或证据不足时明确说明，不将模型推测写成已验证结论；资料存在冲突时指出差异
5. 前端展示回答、引用及相关文档链接；外部API失败时继续使用内部资料，模型生成失败时返回已检索到的文档链接

### 用户反馈

- 回答展示后弹出可关闭的轻提示：“是否解决了你的问题？”，提供“已解决”“未解决”选项，不强制填写
- 选择“未解决”时，可选填写原因，例如未找到资料、回答不准确、资料过期或其他补充说明
- 反馈关联本次请求ID、问题、回答及引用文档，便于定位需要改进的内容或检索环节
- 未反馈不视为已解决；反馈用于发现问题，不等同于对回答正确性的验证
- 初版仅记录反馈，不自动触发文档维护或Wiki评论

### 技术选型与部署约定

目标是在Windows本地开发，部署到Linux单机，尽量减少运行时和独立服务依赖。知识编译层由本项目实现，不依赖同名桌面应用。

| 模块 | 初版选择 | 说明 |
| --- | --- | --- |
| 后端 | Python + FastAPI + Uvicorn | 固定流程编排两路检索与模型调用，使用异步HTTP客户端设置超时和并发上限 |
| 门户 | HTML/CSS/JavaScript静态页面 | 由后端同源提供，覆盖导航、搜索、答案引用和反馈，无需独立前端运行时 |
| 业务存储 | SQLite | 保存同步元数据、问答记录和反馈；使用短事务、写入等待超时，适用于初版单机低写入量场景 |
| 知识编译与检索 | Python编译器、Markdown与SQLite | 根据Karpathy思路生成知识页；SQLite保留查询快照，原文承担最终引用依据 |
| 模型与外部资料 | HTTP API适配器 | 按接口协议接入，模型名、地址、密钥和超时均由配置提供 |
| 后台同步 | 独立Python进程 | 与Web服务共用代码和依赖，定期执行同步；只运行一个同步实例，防止任务重叠 |
| 依赖管理 | uv + pyproject.toml + uv.lock | 固定Python版本和依赖版本；Windows和Linux各自安装依赖，不复制虚拟环境 |
| Linux部署 | Docker Compose | 应用和同步任务使用同一镜像、不同启动命令；提供不用Docker的原生Python启动方式 |

- 数据目录通过配置指定，用跨平台路径处理；不在业务逻辑中依赖PowerShell、Bash、Windows盘符或系统定时任务
- SQLite、原文缓存和索引放在持久化数据目录，容器重建不丢数据；SQLite使用主机本地磁盘，不放在网络共享盘
- 索引更新需保证查询期间可读，采用所选索引组件支持的事务或版本切换方式，接入时验证
- 配置通过环境变量注入，提供不含密钥的配置示例；日志输出到标准输出，提供健康检查接口
- 初版按单机部署，不引入Redis、消息队列或Kubernetes；需要多实例或出现持续写入争用时再评估数据库和任务调度升级
- 若Linux服务器为ARM64，需验证Python依赖兼容性，并构建对应架构镜像；不能直接复用AMD64镜像作为已验证方案
- 上线交付应包含启动说明、持久化目录说明及一致性备份恢复步骤；SQLite使用备份接口或停服务备份，不在写入期间只复制主数据库文件
- 已提供本地启动方式、Dockerfile和Compose配置；Windows已运行验证，Linux容器及ARM64尚未实机验证

参考：[FastAPI容器部署](https://fastapi.tiangolo.com/deployment/docker/)、[uv Docker集成](https://docs.astral.sh/uv/guides/integration/docker/)、[SQLite适用场景](https://www.sqlite.org/whentouse.html)。

### 接入时待确认

- 实际模型API、知识编译效果及每次编译的调用成本
- Wiki接口是否支持版本和删除识别；图片、表格、附件的获取及解析范围
- hisi第三方API的资料覆盖范围、调用方式、限流和超时设置
- 文档同步频率，以及触发外部资料查询的具体条件
- Linux服务器的CPU架构、是否可用Docker，以及访问模型和资料API的网络条件
